1O projeto em 1 minuto

O problema

Reservas em planilha ou e-mail geram a mesma sala, material ou professor alocados duas vezes no mesmo horário, reservas em sala interditada, uso de equipamento caro sem aprovação e nenhum histórico de quem mudou o quê.

O sistema

Um sistema web para reservar salas, professores e materiais sem conflito de horário. Cada reserva aceita é garantida, mesmo quando duas pessoas pedem o mesmo recurso no mesmo instante, e toda mudança fica registrada.

O que é avaliado

Não basta funcionar: é preciso provar com evidência (testes, CI, cobertura, análise estática, carga, rastreabilidade e defeitos registrados).

Os três perfis de usuário

PerfilQuem éO que pode fazer no sistema
Solicitanteprofessor ou coordenadorpesquisar recursos livres, reservar, alterar e cancelar as próprias reservas
Responsávelcoordenador de laboratóriosaprovar ou rejeitar recursos restritos, registrar retirada, devolução e não comparecimento, ver histórico e relatório
Administradorsecretaria acadêmicacadastrar recursos, bloquear para manutenção, ver histórico e relatório

Uma reserva do começo ao fim

1. Loginrecebe um token (JWT)
→
2. Pesquisafiltra por tipo, capacidade, local, competência e horário livre
→
3. Reservanasce SOLICITADA; se o horário já está ocupado → 409
→
4. Aprovaçãorecurso comum: automática · restrito: o Responsável aprova
→
5. Usoretirada → EM_USO · devolução → CONCLUÍDA

Cada passo gera um registro de auditoria imutável e uma notificação (simulada) depois que a mudança é gravada.

Os 4 limitadores de nota (o que derruba a nota, mesmo com o resto bom) 1) aplicação que não executa · 2) pipeline de CI ausente · 3) falha de autorização · 4) possibilidade de dupla reserva.
Por isso o projeto atacou esses quatro primeiro, e cada um tem teste que prova (seção 2).
A frase que resume a disciplina "Uma afirmação de qualidade só vale se aponta para uma evidência e diz o que essa evidência não prova."

3.4 Arquitetura em camadas (de cima para baixo)

Navegador telas (Agenda do dia, Nova reserva, Minhas reservas, Aprovações, Recursos, Manutenção, Relatório)
api + seguranca recebe o pedido HTTP, confere o token e o perfil, valida a entrada, devolve erro em português (ProblemDetail)
servico executa o caso de uso: reservar, aprovar, cancelar, retirar, devolver; grava a auditoria na mesma transação
dominio regras puras: sobreposição de intervalos e transições de estado (as mais testadas)
persistencia / notificacao banco PostgreSQL (com a trava e a constraint) e o envio de aviso para fora

C4 nível 1 — Contexto

Os 3 perfis usam o sistema; o sistema avisa um provedor de notificação externo (simulado) por HTTP.

C4 nível 2 — Contêineres

Só 2 peças: a aplicação Spring Boot (API + telas) e o PostgreSQL. O banco é o ponto único de verdade sobre conflitos.

3.5 Os dados (tabelas)

usuario (perfil, senha com hash BCrypt) · recurso (tipo SALA, MATERIAL ou PROFESSOR, capacidade, local, competências, restrito) · reserva (recurso, solicitante, início, término, estado) · manutencao · auditoria_reserva (quem, quando, estado anterior → novo, motivo) · tentativa_recusada (cada 409, para contar os "conflitos evitados" no relatório).

Ideia-chave: professor também é "recurso"Sala, material e professor ficam na mesma tabela, com um campo tipo. Assim uma só regra de sobreposição protege os três, e a "agenda do professor" (RF-05) sai de graça.

3.6 Máquina de estados da reserva

SOLICITADA→APROVADA→EM_USO→CONCLUIDA alternativos:REJEITADACANCELADANAO_COMPARECEU

Toda reserva nasce SOLICITADA. Recurso comum é aprovado automaticamente; restrito espera o Responsável. Estados finais não mudam mais. Só SOLICITADA, APROVADA e EM_USO ocupam o recurso (cancelada não bloqueia a sala). O teste EstadoReservaTest confere os 49 pares possíveis (7 estados × 7).

3.7 Como a dupla reserva é impedida (a parte mais cobrada)

A e Bpedem a sala 101 no mesmo instante
→
TravaSELECT ... FOR UPDATE no recurso: B espera A terminar
→
A gravareserva + auditoria; COMMIT → 201
→
B conferevê o conflito → ROLLBACK → 409 e grava a tentativa recusada

Duas camadas (ADR-002): a trava por recurso faz os pedidos esperarem a vez (evita deadlock) e a exclusion constraint no PostgreSQL é a garantia final: o banco recusa duas linhas do mesmo recurso com horários que se cruzam, mesmo que alguém grave direto por SQL.

Na prova"Verificar no código se a sala está livre não basta: entre verificar e gravar, outro pedido entra. synchronized também não basta, porque protege uma instância da aplicação, não várias. O banco é o único ponto que todos compartilham."

3.9 Avaliação da arquitetura (ATAM)

Ponto de sensibilidade

O operador < × <= na sobreposição decide sozinho se reservas encostadas conflitam (mutação M1 prova).

Ponto de trade-off

A trava melhora a integridade e piora a latência no pico (medido no DEF-003). Cache de disponibilidade: descartado, poderia mostrar livre uma sala já ocupada.

Riscos tratados

R-01 constraint contando canceladas (só estados que ocupam) · R-02 IDOR (posse no serviço) · R-03 notificação dentro da transação (envio depois do commit).

Não-risco

Queda do provedor de notificação não afeta reservas: o envio é fora da transação e com timeout.

Fontes: docs/arquitetura.md (seção 11) e docs/avaliacao-arquitetural/ciclo-01.md, que refez a análise sobre o código pronto.

4.4 Matriz de autorização

docs/seguranca/matriz-autorizacao.md é uma tabela operação × perfil (anônimo, Solicitante, Responsável, Administrador) com o código esperado (200, 201, 401, 403). O teste lê a própria tabela e executa as 88 células com token real. Mudou a matriz, mudou o teste.

401 Unauthorized

Não está logado (sem token ou token adulterado/vencido).

403 Forbidden

Está logado, mas o perfil não pode (ex.: Solicitante aprovando).

IDOR = trocar o id na URL para mexer na reserva de outro. Células RES-06 e RES-07: o Solicitante tenta cancelar ou alterar a reserva de outro → 403.

4.5 CI, cobertura e análise estática

  • GitHub Actions (workflow qualidade, job test): a cada pull request e a cada push na main, roda ./mvnw -B verify num servidor limpo. Os relatórios ficam guardados 90 dias.
  • Por que verify e não test: o verify roda também os testes de integração e o gate do JaCoCo.
  • Branch protection: a main só aceita merge com o CI verde. Prova da Aula 06 (PR #1): a execução 41207912465 ficou vermelha de propósito e voltou a verde com git revert.
  • JaCoCo: o build falha abaixo de 80% de linhas ou 70% de ramos (provado subindo a meta para 99%).
  • SonarCloud: a 1ª análise achou 12 apontamentos (DEF-004); 11 foram corrigidos e 1 (S4502, CSRF) foi justificado no ADR-007 e aceito. Resultado: Quality Gate aprovado, nota de segurança A.
97,4% no Sonar × 98,0%/95,0% no JaCoCoÉ o mesmo relatório. O Sonar junta linhas e ramos num número só: (583 + 134) ÷ (595 + 141) = 717 ÷ 736 = 97,4%.

Severidade × prioridade

Severidade = tamanho do dano. Prioridade = urgência de corrigir. São independentes.

Erro → defeito → falha

Engano humano → problema no código → comportamento errado que alguém vê.

Na prova: "o DEF-002 aparecia às vezes. Vocês rodaram de novo até passar?"Não. Teste intermitente é defeito a investigar, não "instabilidade". Era deadlock entre pedidos simultâneos; a trava por recurso faz os pedidos do mesmo recurso esperarem a vez. Depois disso, ele ficou 3 rodadas sem "exceções inesperadas", mas 3 rodadas não provam que nunca mais vai acontecer.

Também corrigimos problemas dos testes (não do produto): o teste de concorrência não limpava o banco; a 1ª tentativa da M2 foi inválida sem clean; testes de interface agiam antes de a tela carregar.
